## ⚠️ فروق UralCash عن PicPos — اقراها قبل ما تبدأ

1. **UralCash مطروح وعنده بيانات عملاء.** أي قرار «احذف القديم بدل ما تسنده»
   المتّبع في PicPos **لا ينطبق هنا**. رقعة العروض مصمَّمة على الأساس ده
   تحديداً: الإصلاح في الاستعلام لا في الديالوج، عشان العروض المتخزّنة
   بنهايات منتصف ليل تُقرا صح **من غير هجرة بيانات**.

2. **مفيش تغيير سكيما في أي رقعة** ⇒ **مش محتاج `build_runner`.**
   لو احتجته يوماً: بياخد ~٤١ دقيقة باردة، منها ٤٠ دقيقة تحليل صامت بلا أي
   مخرجات ولا نمو في `.dart_tool/build` — **ما تقتلهوش**، المؤشر الوحيد هو كود
   الخروج. (‏`D:\URAL-ERP` عنده الكاش أصلاً فهيبقى أسرع بكتير.)

3. **الحارس البنيوي الجديد** (`no_bare_client_write_submit_test`) خط أساسه فيه
   مسار خاص بـPicPos (`shift_close_picpos_screen.dart`) **مش موجود عندكم**.
   الماسح بيتخطّى الملفات الغايبة **بقصد** فمش هيفشل. لو ظهر فشل من السطر ده
   يبقى فيه حاجة اتغيّرت — بلّغ ولا تعدّل خط الأساس.

4. **`flutter test --concurrency=1` دايماً، ولا تشغّل عمليتين معاً** — بيتصادموا

## الخطوات

### ٠. قبل أي حاجة — سجّل خط الأساس

مهم: خط أساس UralCash **مش معروف** لي، ومن غيره مش هتقدر تفرّق بين فشل سببه
الرقعة وفشل كان موجود قبلها.

```bash
git status --porcelain          # لازم تكون نضيفة
git rev-parse --abbrev-ref HEAD # سجّل الفرع
flutter analyze lib test 2>&1 | grep -cE " info - "
flutter analyze lib test 2>&1 | grep -cE " (error|warning) - "
```

ثم سجّل أعداد النجاح قبل التركيب:

```bash
flutter test test/unit test/data test/structural test/services --concurrency=1
```

**اكتب الأرقام دي في مكان ما.** كل الحكم بعد كده مقارنة بيها.

### ١. اعمل فرع

```bash
git checkout -b fix/backport-picpos-2026-08-05
```

### ٢. ركّب واحدة واحدة — وتحقّق بعد كل واحدة

لكل رقعة:

```bash
git apply --check <مسار الرقعة>   # لازم يخرج بصفر قبل التركيب الفعلي
git apply <مسار الرقعة>
flutter analyze lib test 2>&1 | grep -E " (error|warning) - "   # لازم فاضي
```

الرقع الثلاث اتأكد إنها بتركّب على شجرة UralCash النضيفة بـ`git apply --check`
(بإزاحات أسطر بسيطة). لو ظهر تعارض، **متجبرهاش بـ`--3way` من غير ما تقرا** —
معناها إن الملف اتغيّر عندكم بعد التوليد، وساعتها الدمج قرار مش إجراء.

### ٣. شغّل الاختبارات الجديدة

الرقع جايبة معاها اختباراتها:

```bash
flutter test test/unit/product_delete_cache_invalidation_test.dart \
             test/unit/offer_end_date_inclusive_test.dart \
             test/unit/product_unit_sale_price_test.dart \
             test/structural --concurrency=1
```

كلها لازم تعدّي. لو واحد فشل، **اقرا نص الفشل قبل ما تعدّل أي حاجة** — الاختبارات
دي اتكتبت تفشل بالأرقام المتوقّعة قبل الإصلاح، فنص الفشل بيقول بالظبط إيه اللي
مش مطابق.

### ٤. السويّة الكاملة ومقارنتها بخط الأساس

```bash
flutter test test/unit test/data test/structural test/services --concurrency=1
flutter test test/integration --concurrency=1
```

المتوقّع: **نفس أعداد خط الأساس + عدد الاختبارات الجديدة** (٤ + ١١ + ٧ + ١
بنيوي = ٢٣). أي نقص = ارتداد، مش تحسّن.

### ٥. تحقّق يدوي — سيناريوهات المختبِر بالحرف

الاختبارات الآلية بتغطي المنطق، لكن دول بلاغات ميدانية فيستحقّوا تشغيل حقيقي:

* **العروض:** اعمل عرض `buy_x_get_y` وعرض `bundle`، وحطّ تاريخ النهاية
  **النهاردة**، وجرّبهم على نقطة البيع. قبل الرقعة الاتنين ما كانوش بيشتغلوا
  خالص؛ بعدها المفروض يشتغلوا طول اليوم.
* **وحدة التعبئة:** افتح صنف، ضيف وحدة «شوال» بمعامل ٥٠، وحطّ **سعر مختلف**
  عن سعر الكيلو × ٥٠. اقفل الصنف وافتحه تاني — السعر لازم يفضل زي ما هو
  (قبل الرقعة كان بيترجع للمشتق مع أول حفظ).
* **حذف صنف:** جرّب حذف صنف على جهاز عميل والسيرفر مقفول. المفروض **يرفض**
  برسالة واضحة بدل ما يختفي ويرجع مع المزامنة.
