# منطق خدمة الطاولات — مواصفة التصميم

**التاريخ:** 2026-08-16
**الفرع:** `claude/tables-reservations-logic-673340`
**النطاق:** الطاولات وحدها. الحجوزات مواصفةٌ مستقلّة لاحقة.

---

## ١. لماذا هذه المواصفة

خدمةُ الطاولات مبنيّةٌ في PicPos بنسبةٍ معتبرة: مخطّطٌ كامل، و‍٦٧٩ سطراً في
`lib/data/database/daos/tables_dao.dart` تُنفّذ الفتح والإضافة والنقل الكامل
والنقل الجزئي والدمج والإغلاق، وستُّ شاشاتٍ فوقها. لكنّ ستّ فجواتٍ تفصل المبنيَّ
عن المطلوب:

1. **حالةُ «طلب مدفوع» 🟠 لا وجود لها.** `finalizeTableOrder`
   ([tables_dao.dart:302](../../../lib/data/database/daos/tables_dao.dart)) يُرجع
   الطاولة `available` فور الدفع، فلا خطوةَ إغلاقٍ صريحة، ولا يعرف النادل أيَّ
   طاولةٍ دُفعت ولم تُجهَّز بعد.
2. **عددُ الأشخاص لا يُخزَّن** في أيّ عمود.
3. **سجلُّ الطاولة غير موجود** كعرض.
4. **الخصم والملاحظات والضريبة ليست على الطلب** — الخصم يُولَد في السلة لحظةَ
   الدفع ويموت معها، فبند «النقل ينقل الخصومات» غيرُ قابلٍ للتحقيق حرفياً.
5. **«تقسيم الفاتورة» الموجود ليس تقسيمَ فاتورة** — `split_table_dialog.dart`
   ينقل أصنافاً إلى طاولةٍ أخرى، لا يقسم حساباً على دافعين.
6. **الكبسات لا تتغيّر حسب الحالة**، فتظهر أفعالٌ لا معنى لها للحالة الراهنة.

ما هو مبنيٌّ ولا يحتاج عملاً: مسارُ التحصيل يُنشئ **فاتورة بيعٍ حقيقيّة** عبر
`checkoutController.processPayment` → `createSalesInvoice` بترحيلٍ محاسبيٍّ وخصمِ
مخزون، ثم يوسمها `saleType='table'`
([table_pos_operations.dart:307](../../../lib/presentation/pos/screens/table_pos_operations.dart)).
و**الدفعُ المختلط مبنيٌّ على مستوى الفاتورة** — `SalesInvoices` تحمل `cashPaid`
و`bankPaid` و`clickPaid` و`paymentMethod='multiple'`. وKDS موصولٌ عبر
`WorkOrders.tableOrderId`.

## ٢. القرارات المتَّخذة

| # | القرار | البديلُ المرفوض ولماذا |
|---|---|---|
| ق١ | **٤ فواتيرَ مستقلّة** عند التقسيم بالأصناف | فاتورةٌ واحدةٌ بأربع دفعات — لا تخدم من يطلب إيصالاً باسمه بأصنافه |
| ق٢ | **بند الطلب يحمل مصدره** بعد الدمج | الدمجُ المسطَّح (الحالي) — يفقد فكَّ الدمج والطباعةَ المجمَّعة ونسبةَ الصنف لنادله |
| ق٣ | **خصمٌ على الطلب + ملاحظةٌ على البند** قبل الدفع | إبقاءُ الخصم لحظةَ الدفع — يُبقي «ينقل الخصومات» كذبةً |
| ق٤ | **طبقةُ خدمة** `TableSessionService` تملك الانتقالات | توسيعٌ في مكانه — يُضخّم mixin الواجهة ويجعل التقسيم (وهو ما يمسّ الدفاتر) غيرَ قابلٍ للاختبار إلا بويدجت |
| ق٥ | **بالتساوي/بمبلغ ⇒ فاتورةٌ واحدة + إيصالٌ لكلّ دافع** | ٤ فواتيرَ بكميّاتٍ كسريّة — مخزونُها سليمٌ لكنّ الإيصال يقول «٠٫٢٥ بطاطا» فيبدو عطلاً |

**مبدأٌ ناظم:** لا تنصيباتِ PicPos قائمةً ولا قواعدَ قديمة، فيُختار التصميمُ
الصحيح لا المتوافق. لذلك تُشطَب مفرداتُ الحالات الميتة بدل تراكمها.

## ٣. آلة الحالات

### حالاتُ الطاولة — خمسٌ لا ثمان

المخطّطُ اليوم يذكر في تعليقٍ ثمانيَ حالات (`available, reserved, occupied,
seated, ordered, eating, billing, cleaning`) أكثرُها غيرُ مستعمَل. تُختصر إلى:

| | الحالة | متى |
|---|---|---|
| 🟢 | `available` | لا طلبَ عليها |
| 🔵 | `occupied` | طلبٌ مفتوح (ولو دُفع منه جزء) |
| 🟠 | `paid` | **جديدة** — سُدِّد كاملاً ولم تُغلَق |
| 🔴 | `reserved` | حجزٌ مسبق |
| ⚪ | `out_of_service` | **جديدة** — خارج الخدمة |

`billing` تُشطَب من حالات الطاولة: طلبُ الفاتورة صفةٌ للطلب
(`TableOrders.status = 'bill_requested'`) وهي موجودةٌ هناك أصلاً.

### الانتقالات

```
available ──فتح (عدد الأشخاص + النادل)──▶ occupied
available ──حجز──▶ reserved ──حضور──▶ occupied
                    └──إلغاء──▶ available
occupied ──نقلٌ كامل / دمجٌ في أخرى / إلغاء الطلب──▶ available
occupied ──اكتمالُ الدفع──▶ paid ──إغلاق──▶ available
paid ──إضافةُ صنف──▶ occupied   (طلبٌ جديد، فاتورةٌ ثانية)
available ◀──تغيير الحالة──▶ out_of_service
```

### قاعدتان تحسمان الرمادي

**ق-أ — الدفعُ الجزئيُّ لا يستحقّ حالةً سادسة.** الطلب يحمل `paidAmount`.
تبقى الطاولة 🔵 حتى `paidAmount >= total`، فتصير 🟠. الحالةُ مشتقّةٌ لا
مُخزَّنةٌ مرّتين. وتعرض البطاقةُ «دُفع ٥٠ من ١٠٠» في الأثناء.

ويترتّب على كونها مشتقّةً أثرٌ مقصود: إن أُضيف صنفٌ إلى طلبٍ دُفع بعضُه، ارتفع
`total` فوق `paidAmount` فعادت الطاولة 🔵 من تلقائها. لا حاجةَ لقاعدةٍ خاصّة.

**ق-ب — بعد 🟠 لا تُضاف أصناف.** إضافةُ صنفٍ بعد اكتمال الدفع تفتح **طلباً
جديداً** على الطاولة نفسها (فاتورةً ثانية) وتُعيدها 🔵. البديلُ — تعديلُ الطلب
المدفوع — يعني تعديلَ فاتورةٍ رُحِّلت محاسبياً وخُصم مخزونُها.

### الكبسات مشتقّةٌ من الحالة

| الكبسة | 🟢 | 🔵 | 🟠 | 🔴 | ⚪ | الصلاحية |
|---|:-:|:-:|:-:|:-:|:-:|---|
| فتح طاولة | ✅ | | | ✅ حضور | | `tables_pos_access` |
| إضافة طلب | | ✅ | ✅ ⟵ طلبٌ جديد | | | `tables_add_items` |
| نقل الطلب | | ✅ | | | | `tables_transfer` |
| دمج الطاولات | | ✅ | | | | `tables_transfer` |
| تقسيم الفاتورة | | ✅ | | | | `tables_checkout` |
| طباعة الفاتورة | | ✅ | ✅ إعادة | | | `tables_print_bill` |
| حجز طاولة | ✅ | | | | | `tables_manage` |
| الدفع | | ✅ | | | | `tables_checkout` |
| تغيير الحالة | ✅ | | | ✅ | ✅ | `tables_manage` |
| **إلغاء الطلب** 🔴 | | ✅ | | | | `tables_cancel` |
| **إغلاق الطاولة** | | | ✅ | | | `tables_pos_access` |
| سجل الطاولة | ✅ | ✅ | ✅ | ✅ | ✅ | `tables_view` |

**فصلٌ مقصود:** «إلغاء الطلب» (على 🔵) هدمٌ يمحو طلباً حيّاً ويلزمه
`tables_cancel`؛ «إغلاق الطاولة» (على 🟠) روتينٌ بلا خطر. جمعُهما تحت اسمٍ
واحدٍ يجعل النادل يمحو طلباً وهو يظنّ أنه يُنظّف طاولة.

## ٤. نموذج البيانات

### ما لا يُلمَس

`SalesInvoices` جدولٌ مشترَكٌ مع UralCash يُنقل بـpatch. لا يُضاف إليه عمود؛
الربطُ يتمّ بجدولٍ محلّيٍّ في ملفات المطعم.

### `TableOrders` — خمسةُ أعمدة

| العمود | النوع | الغرض |
|---|---|---|
| `guestCount` | `int` = 1 | «عدد الأشخاص؟» عند الفتح، وأساسُ التقسيم بالتساوي |
| `notes` | `text?` | ملاحظةُ الطلب |
| `discountType` | `text?` | `percent` \| `amount` |
| `discountValue` | `real` = 0 | يُثبَّت قبل الدفع فينتقل ويُطبع |
| `paidAmount` | `real` = 0 | مجموعُ ما حُصِّل |

`paidAmount` تُصان داخل المعاملة نفسها التي تُنشئ الدفعة، على نمط
`_updateTableOrderTotal` القائم — لا نمطَ ثانٍ في الملف ذاته.

### `TableOrderItems` — عمودان

| العمود | النوع | الغرض |
|---|---|---|
| `notes` | `text?` | «بلا بصل» — تصل المطبخ وتُطبع |
| `sourceTableOrderId` | `int?` → `TableOrders` | مصدرُ البند بعد الدمج؛ فارغٌ للأصناف الأصلية |

### `TableOrderPayments` — جدولٌ جديد

```dart
class TableOrderPayments extends Table {
  IntColumn      get id           => integer().autoIncrement()();
  IntColumn      get tableOrderId => integer().references(TableOrders, #id)();
  IntColumn      get invoiceId    => integer().references(SalesInvoices, #id)();
  RealColumn     get amount       => real()();
  TextColumn     get splitLabel   => text().nullable()();   // «ضيف ١»
  DateTimeColumn get paidAt       => dateTime().withDefault(currentDateAndTime)();
}
```

صفٌّ لكلّ دافع. هو ما يجعل «٤ فواتيرَ لطلبٍ واحد» ممكناً، ويحتمل في الوقت نفسه
حالةَ الفاتورةِ الواحدةِ بعدّة دفعات (يتكرّر `invoiceId`).

### السجل — بلا جدولٍ جديد

`ActivityLogs` موجودٌ ومسلسَلٌ بالهاش (`hash`/`previousHash`, ICR-03) وفيه
`amount` و`oldValue`/`newValue` و`branchId` وأعمدةُ مزامنة
([auth_tables.dart:108](../../../lib/data/database/tables/auth_tables.dart)).
سجلُّ الطاولة استعلامٌ عليه بـ`entityType='table'` و`entityId=tableId`. المكسبُ
الضمني: السجل غيرُ قابلٍ للتزوير بلا سطرٍ إضافيٍّ منّا.

### الصلاحيات

- تُضاف واحدة: `tables_discount`.
- يُرفع وسم «محجوز — الخاصية ما اتبنتش» عن `tables_print_bill`
  ([permission_codes.dart:891](../../../lib/core/permissions/permission_codes.dart)).
- التقسيم يستعمل `tables_checkout`، والدمج يستعمل `tables_transfer` — كلاهما
  نقلُ أصنافٍ بين طاولتين، فلا صلاحيّتين جديدتين.

### الهجرة

أعمدةٌ بقيمٍ افتراضية + جدولٌ واحدٌ جديد ⇒ هجرةٌ إضافيّةٌ بحتة، بلا ترحيل بيانات.

**قيدُ تنفيذٍ إلزامي:** كلُّ تغييرات المخطّط (الأعمدةُ السبعة والجدولُ الجديد)
تُكتب ثم يُشغَّل `build_runner` **مرّةً واحدة**. في هذه البيئة يحتاج ~٤١ دقيقة
ولا يجوز قتلُه، وتحريرُ `database.g.dart` يدوياً يُنقصه ~٤٠٪ بصمتٍ رغم نجاح
`analyze` والاختبارات.

## ٥. العمليات

`TableSessionService` في `lib/services/table_session_service.dart` تملك أحدَ عشرَ
انتقالاً، وكلٌّ منها يكتب سطرَه في `ActivityLogs`. `tables_dao` يعود وصولاً
للبيانات فحسب، والشاشات تنادي الخدمة.

### ١) `openTable({tableId, guestCount, userId})`
- شرط: الطاولة 🟢 أو 🔴 (حضورُ حجز).
- يُنشئ الطلب، الطاولة ⟵ 🔵. سجل: «فتح الطاولة — ٤ أشخاص — أحمد».

### ٢) `addItems` / `removeItem` / `setItemNotes`
- **قاعدةُ السجل:** يُكتب سطرٌ واحدٌ لكلّ دفعةِ «إرسال للمطبخ»، وسطرٌ لكلّ
  **حذفٍ** (هدمٌ يستحقّ أثراً). تسجيلُ كلّ تعديلِ كمّيةٍ يُغرق السجل فيُفقده قيمته.

### ٣) `setOrderDiscount({orderId, type, value})`
- صلاحية `tables_discount`. يُسجَّل بـ`oldValue`/`newValue`.

### ٤) `printBill({orderId})`
- صلاحية `tables_print_bill`. الطلب ⟵ `bill_requested`. الطاولة تبقى 🔵.
- يستعمل محرّك قوالب الطباعة القائم.

### ٥) `transferOrder({fromTableId, toTableId})`
مواصفةُ المالك تُعدّد ما يجب أن ينتقل: رقمُ الطلب، الأصناف، الكميّات، الملاحظات،
الخصومات، الضرائب، الموظف، الإجمالي، الحالة. **هذه كلُّها حقولٌ في صفِّ الطلب
الواحد**، فالنقلُ تحديثُ `tableId` لا غير، وينتقل كلُّ ذلك بلا احتمال ضياع.

- شرط: الهدف 🟢.
- **حارسٌ جديد:** يُرفض إن `paidAmount > 0` — فاتورةٌ صدرت ورُحِّلت ضدّ الطلب.
- المصدر ⟵ 🟢، الهدف ⟵ 🔵. سجل على الطاولتين.

### ٦) `mergeOrders({sourceTableId, targetTableId})`
- يُنقَل سجلُّ كلّ بندٍ موسوماً بـ`sourceTableOrderId`، و**لا تُجمَع كميّاتُ
  المتشابه** — خلافاً للمبنيّ اليوم
  ([tables_dao.dart:510](../../../lib/data/database/daos/tables_dao.dart)).
- `guestCount` يُجمَع. الطلب المصدر ⟵ `closed` بـ`mergedToId`. المصدر ⟵ 🟢.
- **تعارضُ الخصمين:** خصمُ الطاولة الرئيسية يبقى، وخصمُ المدموجة **يسقط**،
  ويُعرَض ذلك صراحةً في نافذة التأكيد ويُكتب في السجل. جمعُ الخصمين يعني أن
  خصماً مُنح لأربعةٍ صار يُطبَّق على ثمانية — تسريبُ مالٍ صامت.
- **حارس:** يُرفض إن `paidAmount > 0` على أيٍّ منهما.

### ٧) `splitBill({orderId, plan, ...})` — انظر §٦

### ٨) `payFull({orderId, paymentResult})`
- فاتورةٌ واحدة عبر مسار التحصيل القائم، صفُّ دفعٍ واحد، `paidAmount = total`،
  الطاولة ⟵ 🟠.

### ٩) `closeTable({tableId})`
- شرط: `paidAmount >= total`. الطاولة ⟵ 🟢. سجل بالمبلغ.

### ١٠) `cancelOrder({tableId})`
- صلاحية `tables_cancel`. شرط: `paidAmount == 0`. الطلب ⟵ `cancelled`،
  الطاولة ⟵ 🟢. يُسجَّل بالمبلغ المهدور.

### ١١) `setTableStatus({tableId, status})`
- بين 🟢 و⚪ فقط. شرط: لا طلبَ نشطاً.

## ٦. تقسيم الفاتورة

### `SplitPlan` — كائنُ قيمةٍ خالص

في `lib/domain/models/split_plan.dart`، بلا أيّ استيرادٍ من `data/database`.
(الحسابُ الخالص مكانُه `domain/models` في هذا المستودع، وحارسُ
`presentation_db_import_guard` يمنع ملفات العرض الجديدة من استيراد القاعدة.)

- `SplitPlan.equal(total, ways)` — الحصصُ متساوية بدقّة
  `AppConstants.decimalPlaces`، **والفرقُ الكسريُّ يُحمَّل على الحصّة الأخيرة**.
  مثال: ١٠٠ ÷ ٣ ⟵ ٣٣٫٣٣٣ + ٣٣٫٣٣٣ + ٣٣٫٣٣٤.
  **ثابتٌ لا يُستثنى: `sum(parts) == total` دائماً.**
- `SplitPlan.byAmounts(total, amounts)` — يرفض ما لا يجمع الإجمالي بالضبط.
- `SplitPlan.byItems(items, assignment)` — يرفض خطّةً تركت بنداً بلا صاحب.

### التنفيذ يفترق حسب الطريقة

| الطريقة | الفواتير | صفوف `TableOrderPayments` | المطبوع |
|---|---|---|---|
| بالأصناف | N — لكلٍّ أصنافُه | N | فاتورةٌ لكلّ ضيف |
| بالتساوي | ١ بكلّ الأصناف | N | إيصالُ حصّةٍ لكلّ دافع |
| بمبلغ | ١ بكلّ الأصناف | N | إيصالُ حصّةٍ لكلّ دافع |

**العلّة في توحيد بالتساوي/بمبلغ على فاتورةٍ واحدة:** لا حدودَ صنفيّةً بينهما،
فإصدارُ N فواتير يعني كميّاتٍ كسريّةً على الإيصال («٠٫٢٥ بطاطا») تبدو للزبون
عطلاً. والمبيعةُ في الحقيقة واحدة، والدافعون عدّة — وهو ما يمثّله
`TableOrderPayments` تماماً. ولا يُمسّ محرّك الفوترة بحرف.

في الحالات الثلاث: `paidAmount` يتراكم، والطاولة تبقى 🔵 حتى اكتمال المبلغ
فتصير 🟠. الدفعُ الجزئيُّ حالةٌ طبيعيّةٌ لا استثناء.

## ٧. الاختبار

الثقلُ على الخدمة والنموذج الخالص، لا على الويدجت: اختباراتُ الويدجت في هذا
المستودع تتعلّق عند فتح الشاشات لأن `db.close()` ينتظر مؤقّت drift في المنطقة
الوهميّة. أيُّ اختبارِ واجهةٍ يجب أن يُفكّك الشجرة ويدفع إطاراً و**لا يُغلق
القاعدة**.

**`SplitPlan` — اختباراتُ وحدةٍ صِرفة (بلا قاعدة):**
- `sum(parts) == total` في ١٠٠÷٣ و١٠٠÷٧ و٠٫٠٠١÷٢
- رفضُ حصّةٍ سالبة أو صفرِ دافعين
- `byAmounts` يرفض مجموعاً مخالفاً
- `byItems` يرفض بنداً غير مُسنَد

**`TableSessionService` على قاعدةٍ في الذاكرة — آلةُ الحالات كاملة:**
- كلُّ انتقالٍ مسموحٍ ينجح، وكلُّ ممنوعٍ يرمي
- نقلُ طلبٍ دُفع منه شيء ⟵ يُرفض
- الدمج: عددُ البنود بعده = مجموعُ البندين (لا تجميعَ كميّات)
- الدمج: خصمُ المصدر يسقط ويُسجَّل
- `paidAmount` يبلغ الإجمالي ⟵ الطاولة 🟠 لا 🟢
- الإغلاق قبل اكتمال الدفع ⟵ يُرفض
- الإضافةُ بعد 🟠 ⟵ طلبٌ جديد والطاولة 🔵

**بوّابةُ الانحدار:** تُقاس سويّةُ `unit` قبل التغيير وبعده؛ الفرقُ وحده دليل.
