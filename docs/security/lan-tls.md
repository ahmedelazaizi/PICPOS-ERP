# LAN transport security (TLS + certificate pinning)

Audit finding **SEC-007**. Status: **fixed in code**, default ON, with an explicit legacy option.

## Behaviour

| Mode | When | What the host serves |
|---|---|---|
| `secure` (**default**) | nothing chosen, or `network_lan_transport=secure` | HTTPS with a **self-signed ECDSA P-256 certificate generated on first run** |
| `custom` | operator configured cert/key files (Network settings) and both paths still exist | HTTPS with the operator's certificate (CA-issued, tunnels...) |
| `legacy_http` | operator explicitly switched it on in the pairing dialog (`network_lan_transport=legacy_http`) | plain HTTP, SECURITY warning in the diagnostic log on every start |

* Mode resolution: `lib/services/lan_tls/lan_tls_manager.dart` (`resolveLanTransportMode`).
  An installation that never chose anything - including every existing install that persisted
  `network_tls_enabled=false` - **becomes secure**. Only the explicit `legacy_http` value keeps HTTP.
* The server **refuses to start** (no silent HTTP fallback) if the managed certificate cannot be
  prepared, or if a configured custom certificate is broken.

## The managed certificate

* Generated by `lib/services/lan_tls/x509_self_signed.dart` (pure Dart, `pointycastle`): ECDSA P-256 / SHA-256,
  10 years, `serverAuth`, SAN = `localhost`, `127.0.0.1` and the host's LAN IPv4.
* Stored **only in the app's secure storage** (`SecureStorageService`: keys `lan_tls_cert_pem`,
  `lan_tls_key_pem`; DPAPI / Keystore backed). It is loaded into a `SecurityContext` from memory
  (`useCertificateChainBytes` / `usePrivateKeyBytes`) - the private key is **never written to a
  loose file and never in the repository**.
* Identity = the SHA-256 fingerprint of the DER certificate. The host IP is not part of it, so an IP
  change does not break paired devices.
* Rotation: *Pairing dialog -> Rotate certificate* generates a new key pair. All paired devices
  must re-pair (their pin no longer matches). Use after a suspected key compromise.

## Pinning (TOFU) in clients

* **Pairing payload** (what the host copies / shows as QR) now contains `serverFingerprint`:
  `{"serverHost","port","pairingCode","serverFingerprint"}`.
* **Desktop client / mirror** (`LanPairingClient.pair`, `TlsTrust`): pasting the payload in the
  pairing-code box pins the fingerprint **before the first request** and uses HTTPS only (no downgrade).
  Typing only the 8-character code uses trust-on-first-use: HTTPS is tried first, the certificate that was
  actually presented is pinned after a successful pairing, and plain HTTP is used only if the host does
  not speak TLS at all. A certificate rejection never falls back to HTTP.
  All later calls (`ServerProxy`, sync, websocket) go through `TlsTrust`, which rejects any certificate
  that does not match the pin.
* **Android apps** (`packages/picpos_api_client`, `lan_pinning.dart`): `LanPairingPayload.parse`
  **refuses** a payload without a fingerprint, and `createPinnedLanClient(fingerprint)` accepts exactly
  that certificate. Release builds stay HTTPS-only: `usesCleartextTraffic="false"`,
  `base-config cleartextTrafficPermitted="false"` and `UrlPolicy.release`
  (guarded by `test/static/distribution_signing_guard_test.dart`).
  The apps' LAN client screens are not built yet (the skeleton has no LAN code); the pinned client is
  the building block they must use.

## Upgrading a fleet

1. Update the **host** first. On its first start it generates the certificate and serves HTTPS.
2. Existing desktop clients/mirrors: open *Network settings -> test connection* once. The scheme
   discovery switches the saved scheme to HTTPS and pins the certificate. (Or re-pair with the payload.)
3. A fleet that still contains clients that cannot do TLS: enable the **legacy HTTP** switch in the
   pairing dialog on the host and restart the server. This is the documented, insecure compatibility
   option - plan to remove it.

## Known behaviour change

The customer-facing QR menu (/menu) is served by the same listener. With TLS on, the QR URL is built from the
active scheme (`https`) and a customer's phone browser shows the usual self-signed-certificate warning. For a
public menu use a tunnel / reverse proxy with a public certificate, or - only if the restaurant accepts cleartext on
its own LAN - the legacy HTTP switch. A separate HTTP-only listener for public pages was not built (owner decision).

## Tests

* `test/security/lan_tls_test.dart` - generator, mode resolution (secure by default / explicit legacy),
  secure-storage manager (first run, reuse, rotate, corrupted store), **real TLS handshakes**: pinned client
  connects, wrong pin rejected (MITM), strict client without a pin rejects the self-signed certificate.
* `test/security/lan_pairing_tls_pin_test.dart` - payload parsing; pairing over real TLS with a correct
  pin, a wrong pin (no HTTP downgrade) and TOFU.
* `packages/picpos_api_client/test/lan_pinning_test.dart` - the Android building blocks.
* `test/unit/go_blockers_tls_pinning_test.dart`, `test/services/network_service_tls_test.dart` - existing.

## Not covered / unverified

* No test starts the real `NetworkService` HTTP server end to end (it needs a database); the server-side
  wiring (`startServer`) was reviewed and compiled, and the building blocks are tested separately.
* A host that is itself behind a tunnel (ngrok etc.) keeps using the tunnel's public certificate.
* The cloud server (`server/`) is separate: see SEC-014 (TLS terminates at a reverse proxy).
