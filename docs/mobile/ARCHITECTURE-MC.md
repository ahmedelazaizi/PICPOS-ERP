# Phase M-C — «PicPos مخازن» Warehouse app (`com.picpos.warehouse`) (Architecture)

> Status: **plan only**. Branch `go/full-remediation` (HEAD `3bcf7158`). Extends `docs/mobile/ARCHITECTURE-M.md` (ADR-M1..M5, §2 contracts, §4 roadmap) — referenced by section number, not repeated.

## 0. Facts that drive the decisions

| Fact observed in current source | Evidence |
|---|---|
| Warehouse stock is authoritative at `(productId, warehouseId)` in `InventoryBalances`; `StockMovements` records warehouse, quantity and reference, but neither table has a bin/location. | `lib/data/database/tables/inventory_tables.dart` (`Warehouses`, `InventoryBalances`, `StockMovements`) |
| `ProductBatches` has warehouse, mandatory expiry, batch number and remaining quantity, but no location. Purchase invoice lines already have nullable `batchNumber`/`expiryDate`; purchase posting creates batches for expiry-tracked items with an expiry. | `lib/data/database/tables/product_tables.dart:217-242`; `lib/data/database/tables/sales_purchase_tables.dart`; `lib/data/database/daos/purchase_dao.dart` |
| `getBatchesForIssue` selects FEFO for `trackExpiry`, FIFO otherwise; `consumeBatchesForIssue` scopes to the issuing warehouse but allows empty/missing batch coverage. `transferStock` posts both warehouse movements and accounting immediately, not dispatch/receipt stages. | `lib/data/database/daos/inventory_batch_dao.dart:21-177`; `lib/data/database/daos/inventory_transfers_dao.dart:45-229` |
| Count tasks store expected quantities and the existing count UI accesses them; current stock requisition status update is a direct write. Blind counting and approved multi-stage handover require new server-side orchestration. | `lib/data/database/daos/cycle_count_dao.dart`; `lib/data/database/daos/inventory_transfers_dao.dart:254-281` |
| `picpos_device` currently provides keyboard-wedge buffering, encrypted local store/outbox and printing; vendor intent/broadcast inputs are not present in its scanner implementation. | `packages/picpos_device/lib/src/scan/scanner_input.dart`; `packages/picpos_device/lib/src/store/`; `packages/picpos_device/lib/src/sync/`; `packages/picpos_device/lib/src/printing/` |

This is a **plan**, not a claim that M-C endpoints, bins or scanner integrations already exist. Base app/relay conventions remain in `docs/mobile/ARCHITECTURE-M.md` ADR-M1..M5, §2 and §4.

## 1. Decision records (ADR-MC1..)

- **ADR-MC1 — Separate offline-first app.** Build `com.picpos.warehouse` beside M-A/M-B, sharing `picpos_ui`, `picpos_api_client`, `picpos_device`, `picpos_rules` per `ARCHITECTURE-M.md` ADR-M1. Use a small encrypted, warehouse-scoped local catalog, task cache and durable command outbox. LAN reaches desktop directly; remote warehouses use the desktop-executed cloud command relay of ADR-M2, not a cloud stock ledger. Neither offline scan nor cloud acceptance means posted stock; show pending/rejected distinctly.
- **ADR-MC2 — One normalized scan pipeline.** Extend `picpos_device` from its existing `KeyboardWedgeBuffer`/`normalizeScan` to `ScannerInput` events `{value,symbology?,source,at}` with camera, keyboard wedge, Zebra DataWedge intent, Honeywell and Urovo broadcast adapters. Validate action/extras against device profiles, dedup camera/intent/wedge echoes within a short configurable window; allow manual entry; do not assume all vendor models use identical extras. Labels resolve product, batch or bin with type-specific validation.
- **ADR-MC3 — Blind counts and segregation.** Desktop creates warehouse/category/location/full-count tasks; counting DTOs and local caches **never include** expected/system qty, stock value, variance or other counters' entries. Submit scanned per-bin counts; desktop privately compares to a frozen baseline and current stock, routes threshold exceedance to an independent recount, and exposes variances only to a manager. A different authorized manager approves before `finalizeCycleCountTask` posts adjustments and the single settlement entry. No offline finalization; use separate count DTO/permission, not the existing `CycleCountItemView` with `expectedQty`.
- **ADR-MC4 — Bin ledger without a second stock truth.** Locations and batch↔location quantities extend warehouse balances/movements; enforce sum of bins equals the existing warehouse balance in one desktop transaction. Backfill all existing balances into one default bin per warehouse; bin movement must never bypass `adjustStock` safeguards/valuation or produce a second GL posting. Location re-slot is a paired bin movement with zero net warehouse/GL effect.
- **ADR-MC5 — Staged documents, desktop execution.** Transfer request → manager approval → scanned FEFO dispatch → scanned receipt and discrepancy resolution (short/over/damaged); van load/unload use the same staged workflow with rep van warehouse. Goods receipt records batch/expiry per PO line and a separate accountant invoice completion. Receipt/issue/damage vouchers require reasons and approval. The present `transferStock` moves and posts **both** sides at once: do not invoke it at dispatch and again at receipt; extract a single controlled posting state machine with in-transit accounting reconciled on receipt, preserving existing immediate-transfer behavior for legacy callers until migrated.

## 2. Scope (release 1)

| Flow | Release-1 behavior and completion boundary |
|---|---|
| Lookup | Barcode/name item search, on-hand per warehouse/bin, batch and expiry, recent movements; offline results labelled with sync time and never treated as reservation or approval. |
| Counts | Desktop assigns cycle or full count by warehouse, category and locations; scan bin then item/batch, enter physical quantity, save/retry offline, submit online; server-driven recount above a configurable absolute or percentage threshold; manager-only variance review and approval before posting. Include zero-stock bins and missing expected lines. |
| Transfers | Request → approve → dispatch FEFO scan pick → destination receive by scan; record partial, short, over and damaged separately, with discrepancy reason and manager resolution; show in-transit quantities; van load/unload use this flow. No automatic over-receipt into saleable stock. |
| PO goods receipt | Scan against PO lines, capture actual quantity, batch number and expiry per expiry-tracked line; record partial/short/over/damaged and quarantine damaged stock; reconcile against ordered/previously received, then hand accepted receipt to accountant to complete supplier invoice — no mobile invoice posting. |
| Stock vouchers | Receipt, issue and damage drafts with reason, location, actor and approval; only approved documents post through desktop stock/accounting paths. |
| Labels | Item and bin barcode label preview/print with template and printer selection; printing failure is retryable and does not post inventory. Desktop location maintenance and label printing are part of the release dependency. |

Out of scope: mobile purchase invoice/accounting completion, stock valuation recalculation on the device, auto-approval of mismatches, cross-company stock, and vendor-specific hardware claims without physical validation.

## 3. Desktop data-model changes

**Proposed desktop raw-SQL migration (SQLite and PostgreSQL equivalents; not implemented):** `warehouse_locations(id,global_id,warehouse_id,aisle,rack,shelf,bin_code,barcode,is_default,is_active,row_version,created_at)` with unique `(warehouse_id,bin_code)` and barcode uniqueness within company; `location_stock(product_id,warehouse_id,location_id,batch_id nullable,quantity,reserved_quantity,updated_at)` unique on the normalized batch key, nonnegative for physically tracked stock; `stock_movements.location_id`, `stock_movements.batch_id` (nullable legacy rows); `product_batch_locations(batch_id,location_id,quantity)` or the equivalent batch-scoped `location_stock` row, never independent competing balances. Add typed `warehouse_docs`/`warehouse_doc_lines` plus scan events and approvals, `warehouse_count_entries` (task, location, product, batch, counter, pass, qty), `warehouse_count_approvals`, and PO receipt lines with cumulative accepted/short/over/damaged quantity and batch/expiry. Extend cycle-count task scope to category/location and distinguish full count, without sending its stored `expectedQty` to counter DTOs. Record global IDs and expected versions for documents/lines, indexed transitions and audit actor/time.

**Backfill:** in a versioned, restart-safe desktop migration create one `DEFAULT` bin per warehouse (including van warehouses); map every existing `(product,warehouse)` `InventoryBalances.quantity` to that bin, map existing warehouse batches to it without duplicating total stock; unbatched remainder stays `batch_id=NULL`. Preserve historical movement `location_id=NULL` rather than falsifying old physical provenance; all **new** stock-changing flows must supply location. Reconcile `SUM(location_stock.quantity)` to `InventoryBalances.quantity` and `SUM(product_batch_locations.quantity)` to each batch's remaining quantity before enabling bin operations; halt rollout on negative/unexplained batch divergence and provide a manager resolution screen. Desktop CRUD screens for aisle/rack/shelf/bin barcode, deactivate-only occupied bins, move stock between bins, print item/bin labels; update desktop report and sync projections to show bin and lot.

**FEFO contract:** under a desktop transaction/stock lock choose only active, positive-quantity lots for the *source warehouse and scanned bin*, reject expired/quarantined lots; for expiry-tracked products sort `(expiryDate ASC, createdAt ASC, batchId ASC)`, then explicit bin tie-break; FIFO otherwise. Reserve a pick atomically, verify each scanned batch/bin against server allocation (manager override recorded, no silent substitute), decrement lot/bin and warehouse totals once on dispatch/issue, credit the same lot to the received bin once on receipt, and reconcile partial/short/over/damage before clearing in-transit. If tracking expiry, receipt requires actual batch and expiry and issue fails closed on insufficient valid batch coverage rather than accepting `consumeBatchesForIssue`'s optional empty result. WAC/GL stays in desktop posting; do not value stock from `ProductBatches.unitCost` alone.

**Current-path impact:** `adjustStock` in `lib/data/database/daos/inventory_dao.dart` already calls `consumeBatchesForIssue` for negative quantity, which selects FEFO when `trackExpiry` (`inventory_batch_dao.dart`); sales mutations call `adjustStock`, so desktop sales and LAN POS posting through sales can inherit warehouse-level FEFO. However the current algorithm has no bin parameter, allows missing batch coverage and does not carry selected lot onto the movement; it cannot prove a physical FEFO pick. `transferStock` calls `adjustStock` out/in, but incoming transfers do not carry the source lot into the destination batch ledger; `repLoadVan`/`repUnloadVan` call that same transfer. Audit every sale/POS/rep sale/return and bulk issue caller, propagate source warehouse/bin/lot through a single issue allocator, explicitly restore the original lot on returns where known, and contract-test warehouse/batch/location conservation before claiming FEFO consistency. PO `convertPOToInvoice` currently combines receipt and invoice and its item mapping omits batch/expiry (`purchase_orders_dao.dart:204-224`); split accepted physical receipt from accountant conversion with a consumed-receipt link to prevent double stock posting.

## 4. API contracts

**Proposed** `/api/m1/wh/*` LAN adapter, not existing routes. Reuse M-A/M-B device pairing, pinned TLS, user session, branch scope, error envelope, `X-Idempotency-Key`, and cloud desktop executor described in `ARCHITECTURE-M.md` §2; authorize each route on desktop, not merely in the UI. JSON quantities are decimal strings in stock units; references use global IDs, timestamps ISO-8601 UTC; reads return `{asOf,serverTime,cursor?,hasMore?}` with bounded pagination and tombstones. Device store caches only warehouse-scoped items/bins/lot metadata, permitted pending tasks and outbox, **never** count baseline or variance.

| Method + proposed LAN path | Request / response (minimum) | Permission |
|---|---|---|
| `GET /api/m1/wh/bootstrap` · `GET /api/m1/wh/pull?entity=&cursor=` | Assigned warehouses, code dictionaries, item/bin/barcode/lot summaries and task headers; incremental scoped rows, server time. During an active count, all bootstrap/pull views for that counter suppress stock quantities, values, variances and competing counts in the task scope. | `warehouse_mobile_access` + read scope |
| `GET /api/m1/wh/items/{globalId}` · `GET /api/m1/wh/movements?item=&cursor=` | Per-warehouse/bin stock and expiry lots, recent movements; explicitly **not** callable with a count-task token while counting the same scope (blind-count leak guard). | `inventory_view` (navigation `stock_view` alone insufficient) |
| `GET /api/m1/wh/counts/tasks` · `POST /api/m1/wh/counts/{id}/entries` · `POST /api/m1/wh/counts/{id}/submit` | Counter DTO `{taskGlobalId,warehouse,locations,productCode,unit,pass}`; entries `{globalId,locationGlobalId,productGlobalId,batchGlobalId?,countedQty,pass,observedAt}`; submit returns `{state:'submitted'|'recount_required'}` only — no expected/variance. | `stock_count_submit` |
| `GET /api/m1/wh/counts/{id}/review` · `POST /api/m1/wh/counts/{id}/approve` | Manager-only baseline, variance and recount comparison; `{commandId,expectedVersion,decision,reason}` → final posting status, using `finalizeCycleCountTask` once after approval. | `stock_adjust_approve` |
| `POST /api/m1/wh/transfers` · `POST /api/m1/wh/transfers/{id}/{approve|dispatch|receive|resolve}` | `{globalId,fromWarehouseGlobalId,toWarehouseGlobalId,lines[]}`; stage commands carry `commandId,expectedVersion,scanLines[{productGlobalId,locationGlobalId,batchGlobalId?,qty}],reason?`; response document state, short/over/damage details, in-transit balance. | `inventory_transfer`; approval additionally `stock_adjust_approve` |
| `POST /api/m1/wh/po/{id}/receipts` · `POST /api/m1/wh/po/receipts/{id}/submit` | `{globalId,expectedVersion,lines[{poLineId,binGlobalId,qty,batchNumber,expiryDate,condition}],reason?}` → accepted/damaged and accountant-pending receipt ref; invoice remains desktop accountant-only. | `goods_receipt_mobile` |
| `POST /api/m1/wh/vouchers` · `POST /api/m1/wh/vouchers/{id}/approve` | `{globalId,type:'in'|'out'|'damage',warehouseGlobalId,reason,lines[]}` → pending then posted/rejected with document ref. | `inventory_edit`; approval `stock_adjust_approve` |
| `GET /api/m1/wh/labels?kind=item|bin&ref=` | Label barcode/print template metadata, no stock mutation. | `inventory_view` / `warehouses_view` |

**Cloud remote path (new, not live):** add warehouse-scoped query/command types to the ADR-M2 `/manage/queries`, `/manage/commands` → `/desktop/relay/next` → desktop executor path (or a separate `/warehouse/*` session façade with **the same** executor and dedup table). Do not copy a warehouse balance into an independently writable cloud ledger. Reads carry desktop `asOf` and stale marker; remote commands stay `queued` until desktop result, and scanning offline only creates locally pending events. Pair and authorize warehouse devices separately from M-A financial access; do not grant `/manage/*` finance merely by holding warehouse credentials.

Every mutation uses client-minted `globalId`/`commandId` as the durable dedup key **across LAN, outbox replay and cloud**, with `X-Idempotency-Key` equal to it; desktop records result before ack and compares canonical payload hash on duplicate (same key/different body → `409 idempotency_conflict`). `expectedVersion` guards state changes; rejected/stale entries stay visible for manual correction, never silently retried with fresh identity. Server enforces warehouse/branch scope, legal transitions, quantity/period/lot rules and separate approver; errors distinguish `permission_denied`, `stale`, `invalid_transition`, `stock_changed`, `batch_expired`, `discrepancy_requires_approval`, `period_closed`, `desktop_offline`. Never include baseline in error bodies or push payloads to counters.

## 5. Permission matrix

Existing code names below are defined in `lib/core/permissions/permission_codes.dart`; proposed codes require registration, role UI, and desktop enforcement. `stock_view`, `stock_audit`, `warehouses_view` are navigation codes (some legacy aliases map to inventory viewing); they must **not** substitute for server-side action checks.

| Operation | Required existing code(s) | Proposed code / rule |
|---|---|---|
| Pair/login app and list assigned warehouses | `warehouses_view` or `inventory_view` | `warehouse_mobile_access`, enabled device/user and assigned warehouse scope |
| Item/bin lookup and movement history | `inventory_view` / `stock_view`; `warehouses_view` for bin metadata | `warehouse_mobile_access`; suppress lookup into active count scope for counter regardless of other read grants |
| Desktop location CRUD/label configuration | `warehouses_manage`; view/print `warehouses_view` | manager-controlled; no count baseline exposure |
| Count tasks and scanned submissions | `stock_audit` / `inventory_view` for desktop task management | `stock_count_submit` + task assignment; no expected qty, variance or approval access |
| Count variance/recount threshold, adjustment approval/finalize | `inventory_edit` / `stock_audit` | `stock_adjust_approve`, manager role, different user from primary counter; server-only `finalizeCycleCountTask` |
| Request/pick/receive transfer, van load/unload | `inventory_transfer` | `warehouse_mobile_access`, origin/destination scope; manager stage approval with `stock_adjust_approve` |
| PO physical goods receipt | desktop purchase-order visibility scoped to warehouse | `goods_receipt_mobile` + assigned destination; accountant alone completes invoice under existing purchase permissions |
| Receipt/issue/damage voucher draft/post | `inventory_edit` | `warehouse_mobile_access` to draft, `stock_adjust_approve` for independent approval/post |

Deny by default if permission mirror is stale or user/device revoked; desktop rechecks actual role and warehouse scope at execution even for cloud-delivered commands. Count and management DTOs must be distinct serializer types; permission-filtering a shared DTO containing `expectedQty` is not acceptable.

## 8. Risks and open questions

| Risk / question | Release-1 default and decision gate |
|---|---|
| Existing batch data may not sum to warehouse stock; expiry mandatory on `ProductBatches` but not on every purchase line. | Backfill untracked difference into the default bin as unbatched; do not invent historical batch/expiry. Block expiry-tracked issues lacking valid lot coverage, route legacy discrepancy to desktop manager reconciliation before enforcing strict FEFO. |
| Current `transferStock` books both legs at once, whereas physical dispatch and receipt are separated. | Design explicit in-transit state, controlled two-stage GL/stock posting and reversal for refused/damaged deliveries; accountant signs off postings before activation. Preserve legacy immediate transfer until parity tests pass. |
| PO conversion now creates invoice and stock together; independent goods receipt risks duplicate inventory or AP. | Introduce durable receipt↔PO↔invoice consumption links and separate goods-received accounting policy; accountant completes invoice only against accepted unbilled quantities; no automatic supplier payable at mobile scan. Confirm goods-in-transit/GRNI account mapping with accountant before release. |
| Counts can be inferred through ordinary lookup or offline caches despite a blind task DTO. | Lock active count scope against lookup for counter on all transports, strip local pre-count stock caches on assignment, never send expected qty/variance to counter, and audit role switching; if the same device had prior stock visibility, require dedicated blind-count mode with cache purge before starting. |
| Concurrent movement between baseline and final count changes adjustment amount. | Manager sees baseline, count-time variance and current on-hand; finalize computes counted minus *fresh* on-hand as existing `finalizeCycleCountTask` does; require recount/reapproval on material intervening change; closed periods reject posting. |
| What threshold and unit precision? | Desktop-configured recount when absolute difference > 0 (conservative default), with optional per-category absolute/% threshold and product-unit rounding; no automatic adjustment even below threshold. |
| Vendor scan intent names, label printer DPI/media and remote latency vary by hardware/site. | Profile each tested model; unknown devices use camera/HID. Print calibrated template per media; queued remote actions retain their status and forbid a second command ID on timeout. |
| Should the app expose cost and multi-company warehouses? | No cost for counters; manager cost only with existing cost permission. One paired company and assigned warehouse set per app profile in release 1; changing company requires explicit wipe/re-pair after outbox drain. |

Decision owners: warehouse lead signs physical flow/threshold, accountant signs transfer and receipt GL design, security lead signs count payload/auth isolation; do not treat these defaults as an implemented guarantee.
