# Supabase Migrations — Dormant

> **QA D5-007 (2026-05-15)**: This directory is **not used by the runtime**.
> It contains a multi-tenant SaaS schema (`tenants`, `user_profiles` →
> `auth.users`) that is unrelated to the Drift schema running in
> client/server mode.

## What the runtime actually uses

The embedded PostgreSQL server (`drift_postgres`, used in client/server
mode) mirrors the local SQLite schema via `_createAllForPostgres` in
[`lib/data/database/database.dart`](../../lib/data/database/database.dart).
That mirror is autogenerated from Drift's table definitions in
[`lib/data/database/tables/`](../../lib/data/database/tables/).

The migrations in this directory are NOT applied at runtime. They are
preserved for a future multi-tenant SaaS launch where the same data
model would back a Supabase-hosted shared database.

**A-SEC-3 / A-SEC-4 (2026-07-02):** the old standalone `supabase_migration.sql`
had NO RLS on any table (incl. `users.password_hash`) and seeded a default
`admin`/`admin` login. Its seeded credential was removed and the file was
quarantined to `supabase_migration.sql.disabled` so no migration tool applies
it. Use only the secure `0001_initial_schema.sql` + `0002_rls_policies.sql`
(default-deny RLS). Extending those policies to every table is a pre-SaaS-launch
task tracked in [`docs/SUPABASE_RLS_CHECKLIST.md`](../../docs/SUPABASE_RLS_CHECKLIST.md).

## Why this README exists

The audit flagged this folder as a source of confusion: a future
contributor reading `supabase/migrations/0001_initial_schema.sql` could
reasonably assume it is the live schema and waste time tracking down
"missing" tables that exist only in the Drift schema.

## What to do if you need to change the live schema

Edit the table definitions under
[`lib/data/database/tables/`](../../lib/data/database/tables/) and bump
`schemaVersion` in [`database.dart`](../../lib/data/database/database.dart).
Add an entry to `migrations/` adjacent to the bump. Do NOT edit the SQL
files in this directory.
